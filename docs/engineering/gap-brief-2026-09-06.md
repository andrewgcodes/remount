# Remount gap brief for engineering — 2026-09-06

Audience: Remount engineers building Remount into the default open-source
runtime SDK for cloud agents.

Scope: this document describes what Remount itself is missing. It
intentionally separates Remount platform gaps from adapter work that belongs
to any one agent product (the originating product is referred to as
"Lakeside" below).

**Owner constraint recorded with the brief:** Remount stays a free,
open-source, self-hosted SDK. Nothing in this brief is to be built as a hosted
product. There will be no Remount-operated dashboard, control plane, or
service; every operator surface named here (console views, conformance
evidence, metrics) is something an adopter runs themselves against their own
deployment. The disposition of each item is tracked in
[the implementation record](./gap-brief-2026-09-06-implementation.md).

## Executive summary

Remount's core abstraction works: a client can create a workspace, run
processes, stream input/output, manipulate files, archive/restore workspace
state, sleep/wake, reconnect, and preserve enough filesystem state for agent
continuation. That is enough for a trusted development preview and enough to
prove that a normal agent loop can be mapped onto Remount.

The remaining gap is not "can Remount run an agent?" It can. The gap is "can
any serious agent company adopt Remount as its default runtime without custom
infrastructure, hidden caveats, or security exceptions?" Not yet.

The five main Remount product gaps are:

1. Turnkey production isolation and backend qualification.
2. Generic brokered identity, credentials, egress, and audit ergonomics.
3. First-class browser/computer-use primitives.
4. Durable lifecycle semantics for running work and background jobs.
5. SDK, conformance, release, observability, and product polish.

There is also one important non-goal: Remount should not become specific to
any one agent product. The fixes below should be expressed as public Remount
APIs and conformance requirements that would also work for Devin, Cursor Cloud
Agent, Harvey, Ramp Inspect, Zendesk, Intercom, OpenEvidence, or another
cloud-agent product.

## Current state worth preserving

These are Remount strengths, not gaps:

- Workspace lifecycle exists: create, claim, readiness, sleep, wake, destroy,
  move/snapshot semantics.
- Process/session IO exists: exec, attach, stdin, output replay, reconnect,
  replay gaps.
- Filesystem APIs exist: read/write/list/mkdir, bounded large writes, archive
  upload/download, scoped restore.
- Workspace ownership/fencing concepts exist: grants, generations, leases,
  state transitions.
- Broker concepts exist: placeholders, bindings, destination allow rules, leak
  blocking, audited credential use.
- Event log and metrics concepts exist.
- Process and Docker backends are useful for development.
- gVisor and Firecracker implementations exist in the tree, with host-specific
  proof lanes.
- The repository already has a strong culture of conformance, fuzzing, race
  tests, and "unavailable is not healthy."

The engineering goal should be to productize and harden these into a stable
runtime platform, not to replace them.

## Priority matrix

| Priority | Gap | Why it matters | Product readiness impact |
|---|---|---|---|
| P0 | Production isolation profile | Multi-tenant agent workloads run untrusted code from many customers. Process/Docker are not enough. | Blocks production multi-tenant default use. |
| P0 | Durable workspace lifecycle for active work | Agents often leave shell commands, browser sessions, downloads, or background jobs running after a turn. A runtime must bound cost without killing needed work. | Blocks reliable agent background work. |
| P0 | Generic identity + credential brokerage | Workspaces must not hold provider credentials, and adopters need a simple safe default. | Blocks secure default adoption. |
| P1 | Browser/computer API | Modern cloud agents need browser automation, screenshots, input, downloads, and sometimes interactive desktop state. | Blocks parity with E2B-like runtimes and agent products with browser tools. |
| P1 | Public conformance and release polish | A runtime SDK must be installable, testable, observable, and stable across languages. | Blocks broad open-source adoption. |
| P2 | Operational ergonomics | Operators need capacity, quotas, cost controls, dashboards, incident tooling, and migration guidance. | Blocks reliable large deployments. |

## Gap 1 — Turnkey production isolation

### Current Remount state

Remount has multiple execution backends. The process backend is explicitly
not isolated. Docker is useful and familiar, but it should not be marketed as
strong isolation between mutually untrusted tenants. gVisor and Firecracker
are the relevant production candidates:

- gVisor can provide stronger syscall/container isolation and deny-first
  networking.
- Firecracker is the microVM-shaped backend closest to E2B-style tenant
  isolation and memory checkpoint aspirations.

The issue is not that the codebase has no isolation work. The issue is that
production safety is still candidate-, host-, kernel-, network-, and
configuration-specific. A new adopter cannot yet run one supported setup path
and get a clear "this fleet satisfies Remount's multi-tenant runtime contract."

### Missing Remount product capability

Remount needs a supported "production isolation profile" that can be
installed, verified, and continuously monitored. That profile should answer:

- Which backend is allowed for multi-tenant untrusted workloads?
- What kernel/KVM/runsc/firewall/cgroup prerequisites are required?
- What Remount config must be set?
- What backend capabilities must be advertised?
- What checks must pass before the node accepts untrusted work?
- What diagnostics prove the environment is safe?
- What behavior is unavailable on this backend?

### Engineering work

Define named runtime profiles:

- `dev`: process/Docker allowed; no multi-tenant security claim.
- `trusted-single-tenant`: Docker/gVisor allowed depending on policy.
- `multi-tenant-isolated`: only backends with verified isolation, deny-first
  egress, cleanup, quotas, and lifecycle fencing.
- `microvm`: Firecracker-only profile with host compatibility checks.

Add a startup gate:

- A node configured for `multi-tenant-isolated` must refuse to serve if it
  cannot prove the backend, network policy, storage, and cleanup boundary.
- A failed or unavailable check must block the node or mark it unschedulable
  for that profile.

Productize exact-host conformance:

- `remount doctor --profile multi-tenant-isolated`
- `remount conformance --profile multi-tenant-isolated`
- machine-readable JSON result with pass/fail/unavailable per check.

Make backend capability claims impossible to fake accidentally:

- The control plane should schedule workloads based on verified backend caps,
  not user-provided labels alone.
- A backend should not advertise `multi_tenant=true` unless the exact runtime
  setup passed the required checks.

Add ongoing drift detection:

- If iptables/nftables/netns/cgroup/KVM prerequisites drift, the node becomes
  unhealthy or unschedulable.
- Emit events and metrics when a node loses an isolation guarantee.

### Acceptance criteria

- A fresh engineer can provision a Remount multi-tenant node from docs and run
  one command to verify it.
- Process and plain Docker nodes cannot accidentally enter a multi-tenant pool.
- gVisor/Firecracker nodes produce explicit pass/fail/unavailable evidence.
- Direct egress from workspace to forbidden destinations is denied before any
  workload code runs.
- Revoking network access kills in-flight forbidden transfers.
- Two mutually untrusted workspaces cannot read each other's files, processes,
  network namespace, or credentials.
- Cleanup removes mounts, namespaces, cgroups, veths, disks, temporary state,
  and Firecracker/runsc leftovers.
- Node crash/restart does not leave unbounded orphaned compute.

### Tests to add or harden

- Exact-host gVisor smoke + denial + cleanup test.
- Exact-host Firecracker boot + exec + snapshot + restore + cleanup test.
- Sibling isolation test: workspace A tries to inspect workspace B.
- Host escape regression tests for mounts, /proc, cgroups, Docker socket,
  netns, and artifact staging.
- Drift test: intentionally break network policy and confirm node becomes
  unschedulable.

## Gap 2 — Generic brokered identity, credentials, egress, and audit

### Current Remount state

Remount already has strong building blocks:

- Workspaces are supposed to receive placeholders, not real credentials.
- The broker substitutes real credentials at the network edge.
- Bindings associate placeholders with approved destinations.
- Credential use, blocked leaks, approvals, budgets, and tenant events are
  represented in the control plane.
- Identity, grants, generations, and revocation concepts exist.

The missing piece is a simple, stable, provider-neutral developer experience
for agent products.

### Missing Remount product capability

An adopter should not need to design their own trust model from scratch.
Remount should expose a default credential/egress model like:

> Create a session-scoped principal, bind it to these destinations and
> capabilities, pass only opaque placeholders into the workspace, and let
> Remount enforce egress, audit, revocation, and budget limits.

That needs to be as easy as creating a workspace.

### Engineering work

Add high-level credential APIs:

- Create session principal.
- Attach destination-scoped binding.
- Rotate/revoke binding.
- List credential-use events.
- Enforce expiration and generation binding.

Standardize binding schemas:

- OpenAI-compatible model APIs.
- Anthropic.
- OpenRouter.
- Browser login/session cookies should be treated separately from API keys.
- Generic HTTP bearer token.
- Generic header/query/body substitution with strict destination scoping.

Make policy explicit:

- Destination allowlist.
- Method/path constraints where relevant.
- Header/body substitution locations.
- Whether approvals are required.
- Budget and rate limits.
- ZDR/data-retention requirements as metadata when providers support it.

Add revocation semantics that engineers can reason about:

- Revoking a principal stops new connections.
- Revoking network kills existing gateway access.
- Revoking a binding prevents further substitution.
- Workspace generation changes invalidate old grants.
- Broker TTL expiry is not the same as provider-side key revocation; document
  this clearly.

Provide SDK-level helpers:

- Go, Python, and TypeScript APIs should expose the same credential workflow.
- Typed errors for denied egress, missing binding, expired grant, approval
  required, quota exceeded, and revocation.

Make audit easy:

- One stream that answers: who/what used which binding, for which workspace,
  to which host, with what status, under which tenant, at what time.
- Never log credential values or sensitive request/response bodies.

### Acceptance criteria

- A workspace can call an approved API using a placeholder without ever
  seeing the real key.
- The same workspace cannot use the placeholder against an unapproved host.
- A leaked placeholder is useless outside its binding/destination/generation.
- Revocation blocks future use and is visible in events.
- A failed/denied request emits a durable event without leaking secrets.
- The SDK has examples for "model API through broker," "search API through
  broker," and "custom HTTP service through broker."
- No first-party example places provider credentials in the workspace
  environment.

### Tests to add or harden

- Placeholder sent to wrong host is blocked and audited.
- Revoked principal cannot create sessions, attach, read files, or use broker.
- Binding revoked mid-stream prevents future upstream bytes where policy
  requires it.
- Error messages redact credentials and credential-shaped strings.
- Concurrent budget reservations cannot overrun limits.
- SDK examples run in CI without real provider keys by using a fake provider.

## Gap 3 — First-class browser/computer-use API

### Current Remount state

Remount can run arbitrary workspace processes. That means a user can install
Chromium, Xvfb, Playwright, VNC/noVNC, screenshot tools, or a custom desktop
daemon inside a workspace. That is not the same as Remount offering a finished
browser/computer-use product surface.

For agent runtimes, browser/computer-use is not optional polish. Many products
need: open URL; screenshot; DOM or accessibility tree capture; click; type;
keypress; scroll; drag; file upload/download; clipboard; viewport sizing;
video/recording; port forwarding; browser profile persistence;
policy-controlled network access; crash recovery and reconnect.

During product testing, browser primitives could launch Chromium and take
screenshots, but reliable text entry was not proven. More importantly, Remount
does not yet define a stable public API for this capability.

### Missing Remount product capability

Remount needs a built-in "computer" or "browser session" abstraction, not
just the ability to run Xvfb manually. Possible shape:

```
computer.create(workspace, profile?)
computer.screenshot(session)
computer.click(session, x, y)
computer.type(session, text)
computer.key(session, key)
computer.scroll(session, dx, dy)
computer.open_url(session, url)
computer.downloads(session)
computer.close(session)
```

This should be backend-independent from the client's perspective.

### Engineering work

Define the public API: coordinate system; screenshot format; input timing
semantics; error types; download/artifact mapping; reconnect behavior; browser
profile persistence; whether DOM/AX tree is part of the API or separate.

Build a reference workspace image: Chromium or equivalent browser;
Xvfb/Wayland or headless mode; fonts, certificates, common file handlers;
Playwright/CDP support; input daemon if not using CDP only; health probe.

Add a Remount-side control daemon or node operation: it should expose
screenshot/input/downloads through Remount, not through an adopter-specific
side channel; it must survive reconnect and report degraded state honestly.

Add policy integration: browser traffic should go through the same
broker/egress controls; downloads should become artifacts with tenant/session
metadata; credentials/cookies must be scoped, revocable, and excluded from
unsafe snapshots when required.

Add recording/trace support: optional video or step trace for debugging;
redaction support for secrets.

### Acceptance criteria

- A clean Remount install can create a browser workspace and run a
  deterministic browser conformance script.
- Screenshot, click, type, keypress, scroll, navigation, downloads, and
  reconnect pass on the supported backend.
- Text input works reliably in ordinary fields and contenteditable fields.
- Browser profile persistence behavior is documented and tested.
- Browser egress obeys Remount policy.
- The API works from Go, Python, and TypeScript clients.
- Failures are typed: browser crashed, display unavailable, input rejected,
  download blocked, navigation denied, profile corrupt, backend unsupported.

### Tests to add

- Open static test page, click button, type into input, assert DOM and
  screenshot changed.
- Type into contenteditable and an iframe.
- Download a file and verify it becomes a Remount artifact.
- Block browser navigation to disallowed host and verify a broker/egress
  event.
- Kill the browser process and verify the client receives a meaningful error.
- Sleep/wake browser workspace and verify documented persistence behavior.

## Gap 4 — Durable lifecycle for running work and background jobs

### Current Remount state

Remount has `ws.sleep`, but its semantics are: sleep pauses/releases the
workspace immediately; `after_sec` or `at` schedules a future resume;
`on_event` schedules event-driven resume.

That is useful, but it does not mean: "Keep this workspace claimed until a
deadline because work is still running, then automatically pause it if nobody
extends the deadline."

That missing behavior matters for any agent product that supports
long-running shell commands, background jobs, browser sessions, downloads,
code servers, approval waits, or tool calls that report back later.

Remount also has agent-level idle policy for Remount's own Agent resource,
but generic workspace clients need an equivalent durable lifecycle primitive
that is not tied to the built-in agent abstraction.

The protocol contains an `Idle` struct with `snapshot_every_sec` and
`destroy_after_sec`, but those fields are not sufficient as currently exposed
for "hold until deadline, then pause" workspace behavior. They also should not
be confused with a client-side timer.

### Missing Remount product capability

Remount needs a durable workspace lease/idle policy API for active work. The
key requirement: **the deadline must live in Remount's control plane, not in
the adopter's API worker process.**

A client-side `asyncio.sleep()` timer can reduce leaks in a preview, but it is
not a complete runtime guarantee. If the client process dies, deploys, loses
network, or is scaled down, the timer dies too. Remount must own the durable
lifecycle deadline.

### Possible API shape

Option A — explicit auto-sleep:

```
ws.keep_awake(workspace_id, until=timestamp, reason="background_job")
ws.auto_sleep(workspace_id, at=timestamp, on_event="session.resume", match={...})
```

Option B — lease extension:

```
ws.lease(workspace_id, min_alive_sec=N, max_alive_sec=M, on_expiry="sleep")
ws.renew_lease(workspace_id, lease_id, min_alive_sec=N)
```

Option C — idle policy:

```
ws.set_idle_policy(workspace_id, sleep_after_sec=N, destroy_after_sec=M?)
ws.mark_idle(workspace_id, reason="turn_settled")
ws.mark_active(workspace_id, reason="new_turn")
```

The best product API may combine B and C: "active lease" for known background
work deadlines; "idle policy" for normal no-work cleanup; "sleep on expiry" as
a durable control-plane action.

### Engineering work

Define the lifecycle state machine: active; idle but held; scheduled-to-sleep;
sleeping/paused; destroyed/quarantined.

Add durable timers in the control plane: survives client disconnect; survives
API worker restart; generation-bound; idempotent; canceled or superseded by
activity.

Add node behavior: on deadline expiry, checkpoint/snapshot as required; kill
or preserve processes according to backend capability; release compute
capacity; emit an event.

Define interaction with active sessions: does expiry send EOF, SIGTERM,
SIGKILL, snapshot memory, or refuse until a command completes? How does a
client reattach after sleep? What does output replay show for work killed by
lifecycle policy?

Define interaction with browser sessions: if a browser is active, can it be
memory-checkpointed? If only filesystem snapshot is supported, what state is
intentionally lost?

Define quota/cost behavior: maximum hold time; per-tenant concurrent held
workspaces; metrics for held compute; events when max hold is reached.

### Acceptance criteria

- A client can say: "Keep this workspace alive for 20 minutes unless I extend
  or cancel it; then sleep it."
- The guarantee survives client process death.
- A new client can inspect the pending lifecycle deadline.
- A new activity cancels or extends the pending sleep according to documented
  rules.
- If the deadline expires, compute is released and an event explains why.
- If sleep fails, Remount retries or marks the workspace degraded; it does not
  silently leak forever.
- Generation changes invalidate stale lifecycle timers.
- The behavior works for raw workspaces, not only Remount's built-in Agent
  resource.

### Tests to add

- Schedule auto-sleep, disconnect client, confirm workspace sleeps after
  deadline.
- Schedule auto-sleep, reconnect before deadline, cancel/extend, confirm no
  premature sleep.
- Cut node connection during deadline expiry, confirm no split-brain and
  eventual cleanup/degraded event.
- Run a long command, auto-sleep at deadline, confirm output replay and exit
  semantics are explicit.
- Move workspace while auto-sleep timer exists, confirm generation fencing.
- Simulate duplicate API retries and confirm one timer/action.

## Gap 5 — SDK, conformance, release, observability, and product polish

### Current Remount state

Remount has Go, Python, and TypeScript surfaces and strong internal tests. It
also has documentation, generated protocol material, a conformance command,
metrics, event logs, and engineering review docs.

The gap is maturity as an open-source default SDK. A broad set of companies
will expect: stable public APIs; semantic versioning; predictable package
releases; examples that run without internal context; conformance tests they
can run against their deployment; clear support matrix by backend and OS;
typed errors; observability integrations; upgrade/migration guidance.

### Missing Remount product capability

Remount needs to feel like a productized runtime SDK, not only a powerful
systems project.

### Engineering work

Stabilize public API contracts: versioned Go module API; published Python
package; published npm package; generated types aligned with protocol; clear
compatibility policy.

Define support matrix: OS (Linux, macOS, Windows client support); backend
(process, Docker, gVisor, Firecracker); feature availability (sleep, move,
memory snapshot, browser, broker, egress, artifacts); production suitability
(dev/trusted/multi-tenant).

Improve typed errors: `PermissionDenied`, `EgressDenied`, `ApprovalRequired`,
`WorkspaceNotReady`, `WorkspaceMoved`, `GenerationMismatch`,
`BackendUnsupported`, `QuotaExceeded`, `OutputEvicted`,
`LifecycleDeadlineExpired`.

Create public examples: minimal remote shell; coding agent loop; brokered
model call; browser session; long-running job with auto-sleep; artifact
upload/download; multi-tenant production profile.

Conformance as a first-class product: `remount conformance --url ... --profile
dev`; `remount conformance --url ... --profile multi-tenant`; JSON and
markdown output; clear "required," "optional," and "unavailable" rows; no row
can pass by being skipped.

Observability: Prometheus metrics for workspaces, sessions, broker decisions,
lifecycle timers, node health, cleanup, quotas; OpenTelemetry traces/spans for
control-plane operations; structured logs with no secrets; operator dashboard
or console views for live workspaces, held compute, blocked egress, failed
cleanup, and lifecycle timers (self-hosted only).

Release discipline: tagged releases; checksums/SBOM; Docker images; published
packages; upgrade notes and migration tests. (Tagging and publishing are
deferred by owner decision; the mechanics are prepared so a later release is
one command.)

### Acceptance criteria

- A new engineer can install the SDK and run examples without reading
  internal docs.
- Public docs state exactly which backend supports which feature.
- Package versions are pinned and reproducible.
- Conformance output can be attached to an engineering review.
- Observability can answer: what is running, why is it running, who owns it,
  how long has it been running, what credentials/egress did it use, and what
  will clean it up?
- An unavailable check is never reported as healthy.

## Cross-cutting requirements

### Security invariants

- Workspaces should not receive provider API keys.
- Credentials should be substituted by the broker only at approved
  destinations.
- Secret values must never appear in logs, events, artifacts, errors,
  examples, screenshots, or docs.
- Tenant identity must be enforced server-side, not by prompt text or UI.
- Grants must remain generation-bound.
- Lifecycle actions must be idempotent.
- Cleanup failures must be observable.
- A failed readiness or isolation check must fail closed.

### Reliability invariants

- Every mutating operation needs an idempotency key.
- State changes need durable events.
- A replay gap must be explicit.
- Client disconnect must not lose output or orphan compute.
- Node loss must eventually produce either recovery or a clear degraded state.
- Timers and lifecycle deadlines must survive client/API-worker restarts.
- Backends must advertise only what they actually support.

### Documentation invariants

- Every user-visible workflow must have an end-to-end example.
- Every backend capability must state its limitations.
- "Verified on candidate X" must not be rewritten into "guaranteed
  generally."
- Host-gated checks must report unavailable when prerequisites are missing.

## Recommended implementation order

1. **Define and ship the production profile gate.** Runtime profile model;
   node startup/scheduling gate; `doctor`/`conformance --profile`; updated
   docs and capability matrix. This prevents overclaiming and gives every
   later feature a truthful safety envelope.
2. **Add durable workspace lifecycle deadlines.** Public workspace lifecycle
   API; control-plane durable timers; generation-bound cancel/extend
   semantics; tests for client death, node loss, retries, and deadline expiry.
3. **Productize brokered credentials.** High-level binding/principal APIs;
   provider-neutral schemas; SDK examples; revocation and audit tests.
4. **Browser/computer-use MVP.** Reference image;
   screenshot/click/type/key/scroll/open/download API; browser conformance
   page and tests; broker-aware browser egress.
5. **Public SDK/release/conformance polish.** Stable API policy; typed errors
   across languages; public examples; observability metrics/traces;
   upgrade/migration docs. Publishing is deferred.

## Concrete "done" checklist

Remount is ready to market as a default cloud-agent runtime when all of these
are true:

- [ ] A new user can create a dev workspace in under 10 minutes.
- [ ] A new operator can provision a verified multi-tenant node from docs.
- [ ] `doctor --profile multi-tenant-isolated` fails closed on missing
      isolation prerequisites.
- [ ] gVisor or Firecracker conformance passes on the intended production
      fleet.
- [ ] Brokered credentials are the documented default path.
- [ ] SDK examples never put provider keys in workspace env.
- [ ] Browser API supports screenshot, click, type, key, scroll, navigation,
      downloads, and reconnect.
- [ ] Workspace lifecycle deadlines are durable across client/API-worker
      death.
- [ ] Long-running commands have explicit expiry/output semantics.
- [ ] Observability shows live workspaces, owners, costs, egress, credential
      use, lifecycle deadlines, and cleanup failures.
- [ ] Go/Python/TypeScript packages are versioned (release deferred).
- [ ] Public conformance can be run against any deployment and produces
      attachable evidence.
- [ ] Docs distinguish dev, trusted single-tenant, and production
      multi-tenant modes.

## What an agent product should not solve for Remount

An agent product can temporarily work around some gaps, but these belong in
Remount:

- Browser/computer-use should not be a product-only daemon.
- Background-job hold/sleep semantics should not rely only on a product
  worker timer.
- Credential brokerage should not be a product-only convention.
- Isolation claims should not depend on product configuration comments.
- Conformance evidence should not live only in a product integration PR.

The right boundary is:

- Remount owns execution, isolation, lifecycle, file/artifact/session APIs,
  brokered credentials, egress, and runtime conformance.
- Agent products own product-specific authorization, user/org/session models,
  prompts, approvals UX, model routing policy, and business logic.

## Short plain-English version

Remount already has the bones of a great agent runtime. What it still needs is
the boring-but-critical product layer: a verified secure production mode, a
safe default way to give agents temporary access without handing them keys, a
real browser/computer API, durable cleanup rules for work that keeps running
after a turn, and polished SDKs/docs/tests that outside teams can trust.

Until those exist, Remount is a strong development/trusted pilot runtime, not
yet the obvious default runtime for every cloud-agent company.
