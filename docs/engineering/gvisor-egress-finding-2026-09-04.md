# The gVisor backend's deny-first egress policy is not enforced — 2026-09-04

**Status:** open, reproduced, with the mechanism identified and the evidence
below. Not fixed. The fix touches a security boundary and wants review.

**Severity:** the workspace network boundary does not hold. Containment on the
host tested here survived only because a *second* boundary — the host's forward
chain — happened to drop the traffic. `EgressMode: "enforced_gateway"` is
advertised unconditionally and is currently unearned.

## How this was found

Plan B B28 has been `unavailable` all along because no host had `runsc`
registered with Docker. That was true of Docker Desktop, whose daemon runs
inside a locked-down LinuxKit VM, but not of the machine: Colima provides a real
Ubuntu 24.04 aarch64 VM with its own Docker daemon, and gVisor installs there
normally. gVisor's `systrap` platform needs no KVM, which is why this works on
Apple Silicon where Firecracker cannot.

With the lane finally runnable, `TestE4DenialConformance` reported six of seven
denial checks passing and one failing:

```
--- FAIL: TestE4DenialConformance/UDP
    forbidden lane succeeded: nc -u -z -w 2 8.8.8.8 53
```

The obvious reading is that UDP is the one hole. That reading is wrong, and the
truth is worse.

## What is actually happening

The workspace network namespace does carry a deny-first policy. Read from
inside the namespace while a sandbox is live:

```
table inet remount {
	chain egress {
		type filter hook output priority filter; policy drop;
		ip daddr 169.254.84.217 tcp dport 40251 accept
	}
	chain forward {
		type filter hook forward priority filter; policy drop;
		...
	}
}
```

And yet, capturing outside the namespace while the suite runs, every forbidden
destination is reached:

```
4  In 169.254.84.218.34337 > 8.8.8.8.53:        (UDP / DNS)
2  In 169.254.84.218.45463 > 203.0.113.1.443:   (CONNECT unlisted target)
2  In 169.254.84.218.28772 > 1.1.1.1.443:       (direct IPv4 TCP)
1  In 169.254.84.218 > 8.8.8.8:                 (ICMP)
```

**All egress leaves the workspace namespace.** The `output` hook never sees it.

The mechanism is that gVisor run with `--network=sandbox` does not use the
namespace's IP stack at all. It runs its own userspace netstack and puts
Ethernet frames onto the veth at the link layer, below netfilter's IP hooks. An
`output`-hook rule filters packets generated by the kernel's own IP stack for
that namespace, and the sandbox generates none. The policy is installed
correctly, on a hook the traffic never traverses.

A control confirms the rule itself works when the traffic does traverse that
hook: in a plain namespace with the same default-drop output chain, a UDP
`sendto` fails with `EPERM`. Inside the gVisor sandbox the identical call
succeeds.

## Why six checks passed anyway, and why that is the real problem

Each passing check asserts that a command *fails*. Every one of them fails for
lack of a **reply**, not for lack of egress:

| Check | Why it "passed" |
|---|---|
| direct IPv4 TCP | SYN leaves; no SYN-ACK returns, so `nc -z` fails |
| CONNECT unlisted target | same |
| DNS | query leaves; no response returns |
| ICMP | echo request leaves; no echo reply returns |
| IPv6 | no IPv6 route configured |
| raw socket | blocked inside gVisor by `--net-raw=false` |
| **UDP** | **needs no reply, so nothing hides the egress** |

The return path is blocked by the host's forward chain, one boundary further
out. So six of the seven checks would pass against a completely open egress
path as long as replies were dropped somewhere. **The suite cannot distinguish
"egress denied" from "replies blocked."** Only the UDP lane, which requires no
reply, exposes the difference — and one-way egress is all that data
exfiltration needs.

Verified: nothing reached the internet. Capturing on the VM's external
interface during a full run showed **0 packets** to any forbidden destination.
The outer boundary holds on this host. That is defence in depth doing its job,
and it is not the property the workspace boundary is supposed to provide.

## The capability claim

`internal/workspace/gvisor/gvisor.go:98` returns
`EgressMode: "enforced_gateway"` unconditionally, and
`internal/proto/proto.go:732` admits a workspace that sets
`RequireEnforcedEgress` onto any backend making that claim. So a workspace that
explicitly demands enforced egress is placed on a backend where, as measured,
egress is not enforced at the workspace boundary.

`docs/engineering/handoff-linux-host-2026-09-03.md` §1 already states the rule
this violates: "The backend may advertise `enforced_gateway` **only** after that
suite passes on the exact candidate. Do not claim `isolated` or `multi_tenant`
from a passing unit test. The capability is earned by the probe, not by the code
existing."

## What the fix has to do

Enforce on a hook that sees link-layer-injected traffic. The natural place is
the host side of the veth, as a `netdev` filter:

```
table netdev remount {
  chain rmh<n> { type filter hook ingress device "rmh<n>" priority 0; policy drop; ... }
}
```

An `ingress` netdev hook sees frames as they arrive from the peer regardless of
how the peer produced them, so AF_PACKET injection cannot bypass it. Kernels
5.16+ also offer `hook egress` for the symmetric direction.

This is deliberately not attempted here. It is a security boundary, the rule
set has to keep permitting exactly the broker address and port and nothing else,
and it needs to be proven by the same capture method used above rather than by a
rule existing. Whoever takes it should also decide whether
`EgressMode: "enforced_gateway"` may be returned at all before the probe passes.

## Reproducing

Requires a Linux host with `runsc` registered. On macOS, `colima start` provides
one; `runsc install` registers the runtime.

```sh
# in the VM
export REMOUNT_GVISOR_INTEGRATION=1 REMOUNT_GVISOR_ROOTFS=/var/tmp/gvisor-rootfs
nohup tcpdump -i any -n -c 40 'host 1.1.1.1 or host 8.8.8.8 or host 203.0.113.1' > /tmp/all.txt &
go test -count=1 -run TestE4DenialConformance ./internal/workspace/gvisor/
awk '{print $3, $5, $6, $7}' /tmp/all.txt | sort | uniq -c | sort -rn
```

Any line whose source is the sandbox address is traffic that crossed the
boundary. There should be none.

Note that a killed run leaves state behind that makes the next run fail on
`create veth: file exists` or `create network namespace: ... file exists`; see
the resource-leak finding recorded alongside this one.

# Second finding: a killed run leaks every resource it created

Separate from the egress finding, and found the same way. When the gVisor
integration test is killed — a test timeout, SIGKILL, a crashed node — nothing
reclaims what the backend created:

| Leaked | Symptom on the next run |
|---|---|
| the netns bind mount `/run/remount/netns/rm-<pid>-<n>` | `create network namespace: ... file exists` |
| the veth `rmh<pid>` | `create veth: file exists` |
| the `runsc-sandbox` and `runsc-gofer` processes | none, they simply run forever |

The orphaned sandboxes are the worst of the three because they are silent. One
observed here had been running **1733 seconds** after the test that created it
was killed, holding its memory and its gofer.

The names are derived from the creating process's PID, so this is not merely
untidy: a later process that happens to get the same PID collides and cannot
start a workspace at all. On a machine where PIDs recycle quickly, a node that
crashed once can be unable to create workspaces afterwards, with an error that
names a file rather than the cause.

A node has no startup reconciliation for these. `docs/engineering/handoff-linux-host-2026-09-03.md`
§1 asks that "cleanup runs after every failure path"; cleanup does run on the
error paths inside the process, and does not run when the process is not there
to run it, which is exactly when it matters.

What a fix needs: a reaper at backend startup that removes netns files and veths
whose owning PID is gone, and kills sandboxes whose workspace this node does not
hold. The existing `consistency.orphan_on_node` doctor check covers the control
plane's view of workspaces, not host resources beneath a dead node.

A cleanup script sufficient for a developer host, used while investigating:

```sh
pkill -9 -f runsc
for f in /run/remount/netns/*; do umount "$f" 2>/dev/null; rm -f "$f"; done
ip -o link show | sed -n 's/^[0-9]*: \([^:@]*\).*/\1/p' | grep '^rm' |
  while read -r l; do ip link del "$l"; done
```

# Third finding: the docker backend does not check that the daemon can see the workspace

Found incidentally, because pointing `docker` at the Colima VM changed which
daemon the docker backend talked to. `TestDockerBackendReal` then failed like
this:

```
"ws_dk\n/work\ncat: can't open 'f.txt': No such file or directory\n"
```

Read that carefully. `Create` succeeded. `FS().Write("f.txt", ...)` succeeded.
The container started, reported its workspace id and its `/work` directory
correctly, and could not see the file the node had just written into it.

The docker backend bind-mounts the node's data directory into the container, so
it assumes the daemon shares a filesystem with the node. When the daemon is
remote — a VM, a socket forwarded from another machine, a CI runner with a
daemon in a sidecar — that assumption is false, and the result is not an error.
It is a workspace that starts, accepts writes, runs sessions, and silently has
none of the node's data in it.

The node already probes for a related property: it drops the read-only volume
backend when a bind-mount probe fails, logging `read-only volumes unavailable`.
There is no equivalent probe for the workspace root itself, which is the more
important of the two.

What a fix needs: at backend construction, write a known byte into the data
directory, run a throwaway container with the same bind mount, and read it back.
If the daemon cannot see it, refuse to offer the docker backend rather than
offering one that loses data. That is the same shape as the volume probe and the
same shape as the gVisor denial probe: a capability is earned by demonstrating
it, not by the code existing.
